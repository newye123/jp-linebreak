# 案例 01：四条用例，零条断言

## 症状

仓库里有个 `api/test-segments.js`。它定义四个 `testCases`，逐个跑，把断行结果打印出来：

```
【基础日文文本】
原文: 今日はいい天気ですね。散歩に行きませんか？
断行结果:
  1: 今日はいい天気です
  2: ね。散歩に行きませんか？
统计: 21字 -> 2行
```

四个用例全部「通过」，退出码 `0`。CI 里挂上去就是绿的。

而下面这四行，全是同一份输出里的：

```
  2: 。特に問題は（ありません）。
  3: 。
  4: 。今後もより
  6: 。
```

行首是「。」。这不是排版偏好问题，是日文组版的硬规则（行頭禁則，JIS X 4051）：
句号、读点、闭括号、小写假名不能出现在行首。任何一本日文排版手册的第一页就是这个。

## 取证

```console
$ node api/test-segments.js > /tmp/ts.out 2>&1; echo "rc=$?"
rc=0

$ grep -nE '^  [0-9]+: [。、！？）」』】]' /tmp/ts.out
23:  2: 。特に問題は（ありません）。
36:  3: 。
50:  4: 。今後もより
52:  6: 。
```

四条用例，四处行頭禁則违反，退出码 0。

同一批文本，新旧实现对跑，用 `tools/check-kinsoku.js` 数：

```console
$ node tools/check-kinsoku.js fixtures/before.txt
fixtures/before.txt: 13 行，6 违反
  行頭禁則 第 4 行  「。」  。特に問題は（ありません）。
  行頭禁則 第 7 行  「。」  。
  1文字行 第 7 行  「。」  。
  行頭禁則 第 11 行  「。」  。今後もより
  行頭禁則 第 13 行  「。」  。
  1文字行 第 13 行  「。」  。
rc=1

$ node tools/check-kinsoku.js fixtures/after.txt
fixtures/after.txt: 11 行，0 违反
rc=0
```

`fixtures/before.txt` 就是旧实现的原始输出，一字未改；`fixtures/after.txt` 是新输出。

## 根因

三件事叠在一起：

1. **文件名承诺了它没做的事。** 叫 `test`，实际是 demo。它验证的是「脚本没崩」，不是「排版对不对」。
2. **退出码只有一档。** `console.log` 写完就是 `0`。不管印出来的是不是「。」开头，只要没抛异常就是绿。**一个永远不会红的检查器，比没有检查器更糟** —— 它会让人停止检查。
3. **人眼读不出来。** 「。」开头的行在终端里只是短一点的一行，没有对比就看不见。这不是不够细心，是这种错误本来就该由机器看。

## 修法

断言分三层，各自抓不同的东西：

| 层 | 抓什么 | 例子 |
|---|---|---|
| golden | 规则表被悄悄改动 | `'今日はいい天気ですね。散歩に行きませんか？'` max=15 必须切成 `['今日はいい天気ですね。','散歩に行きませんか？']` |
| property | 任意输入都该成立的不变量 | 4 ≤ max ≤ 30、10 段语料，输出里行頭禁則违反必须是 0；`lines.join('') === 原文` |
| regression | 旧的坏输出不再出现 | `fixtures/before.txt` 里至少有 4 处违反（证明 fixture 没被改好），`after.txt` 里 0 处 |

CLI 的退出码改成三档，见 `tools/check-kinsoku.js`：

- `0` 查过了，零违反
- `1` 查过了，有违反
- `2` 没查成 —— 路径错、文件空、一行有效内容都没有

第三档是关键。如果「没读到东西」也返回 `0`，那么路径打错、文件为空、编码读错，全部会被读成「干净」。

### 写断言当天就抓到的第二个洞

补测试的时候顺手加了一条「把 `preferAfterParticle` 关掉，结果必须变」—— 想证明这个选项是活的。它红了。

```js
// 第一版：
const tail2 = text.slice(i - 1, i + 1)   // 2 个字符
PARTICLES_SINGLE.indexOf(tail2)          // 表里全是 1 个字符的助词
```

两边长度永远对不上，助词分支从来没命中过。`preferAfterParticle` 是个死开关：传 `true` 传 `false` 输出一样。

这条洞用真实文档跑一万遍也发现不了 —— 死开关不会让输出变丑，只会让输出**不按你说的那样变**。只有「打开它和关掉它结果必须不同」这种断言看得见它。

## 结论

**「跑通了」和「对了」是两件事，而 `console.log` 只证明第一件。**

判断一份测试值不值钱，不看它打印了什么，看它红过没有。如果一段测试从写下到现在从没红过，它可能只是在记录当前行为 —— 而当前行为可以是错的。

配套动作：`tests/repo.test.js` 里加了一条守卫，断言每个 `*.test.js` 里 `assert` 出现的次数不少于 `test(` 的次数。这条守卫不完美（它数的是字符串，不是 AST），但它能挡住「新增一个只打印不断言的测试文件」这件事本身。
